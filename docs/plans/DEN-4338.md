# DEN-4338 — Unblock Slack threads after message edits and coding outcomes

## Problem

1. **Edited-reply retrieval.** The coordinator reads an edited original separately with a bounded
   `conversations.replies` call (`oldest = latest = originalTs`). Slack always returns the thread parent
   first, so the response holds `[parent, editedReply]`. The coordinator required exactly one message and
   threw `returned unexpected edited message`. The pending edit was never marked processed, so it blocked
   later messages and research-result coordination in the thread.
2. **Coding results.** `rowToSlackTask` treated any non-null `result_json` as a research answer and threw
   `Coding task … has a research result`. Coding completion (`complete()`) and crash recovery
   (`sqliteApplyRecovery()`/`pgApplyRecovery()`) legitimately store a `DispatchResult` there, so every later
   message in such a thread failed with that error.

## Changes

- `src/manager/slack-thread-api.ts`: add `readThreadMessage(key, ts)`. It does the bounded read, drops the
  thread parent unless the parent is the target, and then:
  - returns `null` when the target is gone (so the deleted-original abandonment path still works);
  - returns the message when exactly the requested message remains;
  - throws on unexpected or duplicate messages. Pagination is still rejected by `readThread`.
- `src/manager/slack-coordinator.ts`: use `readThreadMessage` for edited originals.
- `src/db/client.ts`: check `result_json` against the task type. Coding rows go through the existing
  strict `validateStoredDispatchResult` check (the lenient `parseDispatchResult` coerces bad shapes): the
  payload must be a non-empty JSON object with `status` `pending`/`done`, an optional boolean
  `notifyOnComplete`, and either a `prs` array of PR refs (non-empty `owner`/`repo`, positive integer
  `number`) or the legacy single `pr` (ref or `null`). Any other shape throws with the task ID. Research
  rows keep the strict answer/summary checks, and non-JSON/non-object research payloads also throw with the
  task ID. `SlackTaskRecord.result`/`summary` hold only the research answer and stay `null`
  for coding tasks.

There are no schema or data changes. Pending edits, later messages, and completed research that is
`awaiting_coordination` resume on the next coordinator poll after deployment.
