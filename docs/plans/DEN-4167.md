# DEN-4167 — Make Slack notification failures traceable

## Goal

Every Bear Metal Slack notification failure (PR opened/updated/CI-delayed,
needs-input, max-iterations) must be diagnosable from logs, and must not be
silently recorded as a successful send.

Concretely:

- Log the notification decision, send attempt, and failure with `ticketId`,
  `notificationKind`, `prRef` (when relevant), `destinationType` (`dm` or
  `channel`), and `stage`. Include HTTP status, Slack error code, or the
  thrown exception. **Never** log tokens, message body text, or channel ids
  as message content.
- Surface `chat.postMessage` failures to callers (non-2xx, `ok=false`,
  network exception, timeout). Today the integration swallows all three and
  the scheduler happily records `user_notified` events / sets `pr.notified_at`
  as if the send succeeded — that is the root cause of DEN-4160's
  "PR opened without a recorded notification" (or would be the root cause if
  Slack starts failing silently in future). A failed post must not create a
  `user_notified` event and must not set `pr.notified_at`.
- Keep the existing no-retry policy: one send attempt per decision, log, done.
  No queues, no monitoring system, no task-status redesign.

## Changes

### `bear-metal/src/shared/integrations/slack/client.ts`

- `postMessage` now `throw`s on HTTP non-2xx, on Slack `ok=false`, and on
  any thrown/rejected fetch (network + `AbortError` timeouts). Structured
  logs at each stage: `attempting`, `sent`, `failed`. The log payload
  includes `ticketId`, `notificationKind`, `destinationType`, and (for PR
  notifications) `prRefs: [{owner,repo,number}]`. On failure the log payload
  includes `httpStatus` / `slackError` / `err` — but never the token, the
  message body, or the resolved DM channel id string as a value the caller
  reads (channel id is safe to log for debugging; token is not).
- `resolveUserChannel` returns both the target channel id and a
  `destinationType` so callers can log which surface was used. Recipient
  lookup fallback continues to warn (channel + `email` + error), unchanged.
- Each `notify*` method emits a `decision` log at the start (kind, ticketId,
  destinationType, prRefs) and propagates any error from `postMessage`.

### `bear-metal/src/manager/scheduler.ts`

- PR notification loop is extracted to `sendPullRequestNotifications` and
  called from `refreshTrackedTickets`. Each notification kind (`opened`,
  `updated`, `validation_delayed`) runs inside its own `try` so a Slack
  failure on one kind does not skip the others. On thrown failure, log
  `slack notifyPullRequest failed` with `ticketId`, `ticketIdentifier`,
  `notificationKind`, `prRefs`, `stage="failed"`, `err`, and **do not**
  call `db.markPrNotified` or record a `user_notified` event. On success,
  keep current behavior (mark + event).
- `notifyNeedsInput` and `notifyMaxIterationsReached` callers already wrap
  the call in `try/catch`; keep that, but tighten so the `user_notified`
  event for max-iterations is only written when the send actually
  succeeded (it already is — verify and add regression test).
- Add explicit pre-send skip logs where the scheduler currently proceeds
  silently: `slack integration not configured; skipping X` and
  `no PRs in ticket context; skipping PR notification`.

### Tests

- `slack/client.test.ts`: replace the three existing "logs errors but does
  not throw" tests with tests that assert `notify*` **rejects** on HTTP
  error, on `ok=false`, and on thrown fetch. Add coverage that failure logs
  carry `ticketId`, `notificationKind`, `stage="failed"`, `httpStatus` or
  `slackError`.
- `scheduler.test.ts`: add tests that when Slack throws for a PR
  notification, the ticket's PR is **not** marked as notified in the DB
  and **no** `user_notified` event is recorded. Same for the
  max-iterations path. Add a cascade-isolation test with two PRs (one
  `opened`, one `updated`) where only the `opened` kind throws and assert
  that the `updated` `user_notified` event is still recorded.

## Verification

- `npm test` in `bear-metal/`.
- Skim the logger output shape by unit-testing a captured logger with a
  memory transport to verify the required fields are present.

## Non-goals

Retry queue, notification pipeline, monitoring system, task-status redesign.
