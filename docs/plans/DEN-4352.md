# DEN-4352 — Prevent lost Slack PR notifications when tasks finish during scheduler polling

## Problem

`refreshTrackedTickets` iterates a `db.listTracked()` snapshot and awaits
`linear.getTicket()` per slot. If the worker completes the slot's running task
during that await, the worker stores `result.prs` and sets the ticket to
`validating / notify=1`. The scheduler then derives PRs from the stale running
task input (empty), while `tryTransitionToWaitingForHuman()` reads the fresh
`validating / notify=1` row, clears `notify`, and returns true. The empty PR
list makes the scheduler log `no PRs in ticket context; skipping PR
notification` — the intent is gone and later polls never notify.

## Changes

### `src/db/client.ts`

- `getTrackedSlot(ticketId)`: re-read the ticket's latest tracked task (same
  filter as `listTracked`), or `null` if the slot was released.
- `tryTransitionToWaitingForHuman(ticketId, completedTaskId)`:
  - transitions `validating → waiting_for_human` only while `completedTaskId`
    is still the ticket's latest tracked task and is completed;
  - no longer clears `notify`; returns whether a PR notification is pending
    for that task (`status = waiting_for_human AND notify = 1`, same guard).
    A ticket whose earlier send failed or was skipped stays pending.
- `clearPendingNotification(ticketId, completedTaskId)`: clears `notify` after
  delivery is confirmed, unless a newer task for the ticket has already
  completed (its own intent must survive).

### `src/manager/scheduler.ts`

- After the Linear await, replace the snapshot with `getTrackedSlot()` so the
  decision uses current task/result data; skip the slot if it was released.
- Only attempt the transition when the latest task is completed; a running
  task never moves the ticket to `waiting_for_human`.
- PRs for the notification come from the completed task result. Missing Slack
  or an empty PR list logs and keeps the intent pending.
- `sendPullRequestNotifications` returns whether every PR group was accepted
  by Slack. Only full success clears the intent. PRs already delivered for the
  current task are remembered in-memory per ticket so a retry after partial
  failure does not resend them (same lifetime model as the CI-deferral timer).
- Unchanged: CI deferral, bot-review / CI iteration dispatch, recipient
  routing, grouped opened/updated/validation_delayed messages, success-only
  `notified_at` / `user_notified` bookkeeping.

## Tests (`src/manager/scheduler.test.ts`, real `Scheduler` + `SqlDbClient` on SQLite)

Written first and confirmed failing on `main`:

- Race: running task in the snapshot; the worker completes and sets
  `validating, notify=1` inside `linear.getTicket()`. Expect the PR
  notification on the same tick, `notified_at` set, `user_notified` recorded,
  `notify=0`; a second tick sends nothing more.
- Failed send keeps `waiting_for_human, notify=1`; the next tick delivers and
  clears the intent.
- Partial multi-PR failure retries only the failed group.
- Slack not configured keeps the intent pending.
- Bot-review iteration: intent from the first task survives a re-dispatch and
  is delivered after the second task completes.
- Existing ordinary completion, CI deferral, validation-delayed, and multi-PR
  grouping tests keep passing. The existing failed-send test's
  `notify: 0` expectation encoded the bug and now expects `notify: 1`.
