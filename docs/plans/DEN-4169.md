# DEN-4169 — Bear Metal in Slack threads

## Goal

An `@Bear Metal` mention joins a Slack thread and may itself contain actionable requests. Bear Metal then handles requests directed at it in later replies, even without another mention. Earlier thread messages are context only. Its own messages never trigger work.

## Glossary

**Coordinator:** A Pi run started by the manager to decide what a thread's new messages mean and which tasks or replies to create, update, or cancel.

## Runtime

- Two coordinator runs on one thread could both create a task for the same message, or an old answer could post after a correction. Therefore, run one coordinator at a time per thread. Exactly one manager process owns an in-memory queue keyed by `(workspace ID, channel ID, root thread_ts)`; different threads may run concurrently. Node's single event loop alone does not serialize async runs. No cross-thread task coordination or long-lived DB lock.
- Subscribe the Slack app to mentions and message events in public channels, private channels, and DMs, with Slack Delayed Events enabled. Verify incoming requests, durably record the message reference, acknowledge Slack within three seconds, and queue coordination. Slack retries unacknowledged events; Delayed Events extends retries during outages. The app subscription persists across process restarts; there is no per-thread Slack subscription. Deduplicate mention/message events and retries by `(workspace ID, channel ID, message ts)`.
- On a first mention, store the root thread key and the mention's `ts`. Every new top-level DM to Bear Metal likewise activates a thread, with replies posted under that root. Process the activating message and later replies. Fetch all available unprocessed replies before each coordinator prompt, including replies that arrived while a prior run was active; paginate rather than silently truncating. The prompt tells Pi it can use `slack_read` to read earlier messages for context, but only the unprocessed messages are requests to act on.
- Give the coordinator a structured JSON payload of unprocessed messages and concise ongoing-task summaries: IDs, source-message references, identifying question quotes, and status. Bound individual message text and aggregate message text with explicit truncation metadata and references for full Slack reads. Keep larger task request/result data out of the prompt and expose task details through a tool. It acts on requests still open after later corrections or answers in the batch. It marks every considered message processed, including messages with no actionable task.
- A wake during an active run coalesces into a subsequent pass for that thread. Completing a research task immediately wakes its coordinator; each manager poll also finds tasks awaiting coordination after a missed wake or restart. A poll checks for work, enters the keyed queue, then checks again; duplicate wakes become no-ops. On restart, rebuild queues from durable inbox and task state. Do not attempt to query missing events from slack.

## Tasks and tools

- Reuse the existing `tasks` table. Add a general coding/research task type plus optional Slack thread and source-message references. Existing Linear coding runs keep their behavior. A message with several independent requests creates one task row per request; do not add a separate Slack task table or actions table.
- Expose coordinator tools to create, update, and cancel coding and research tasks. The coordinator calls Linear to create a coding ticket through the coding-task tool; a coding task does not implement code. Store the resulting ticket link on that task and reply in the Slack thread immediately after successful creation. Existing Linear delegation handles any later implementation.
- For a follow-up correction to research, build the replacement worker request from the prior persisted request and the new correction, with the newest conflicting detail taking precedence. A Slack edit supplies the complete edited request. This preserves the original question's scope and source references across multiple follow-ups.
- For each research task, pass its type and request to `customizeTask`, run the existing required `buildWorkspace` hook, and run Pi in `BEAR_METAL_WORKSPACE_DIR/research/<task ID>/agent`. Remove the task workspace after the run, as with coding tasks. The research worker can use existing Slack, Linear, GitHub, and web read tools. Defer dynamic cloning during a run and custom task types, while keeping task dispatch extensible.
- Coordinator runs share a checkout under `BEAR_METAL_WORKSPACE_DIR/coordinator`, built with the coordinator task's configured `buildWorkspace` hook. Refresh it every 24 hours through a new complete generation; active runs finish against the old generation before it is deleted. Inject the checkout's root `AGENTS.md` and give the coordinator only read, list, find, and grep file tools. The checkout is rebuilt after a manager restart.
- The coordinator chooses a short, identifying quote of the user question and stores it with the research task. The research-answer tool accepts the answer and writes it to that task's `result_json`, setting `awaiting_coordination`; it does not post to Slack. It wakes the owning thread queue. Polling finds the same state after a missed wake or restart.
- The coordinator checks whether a completed task is still current, posts the stored quote and answer in the thread, then records the Slack reply `ts` and `coordinated_at` on the task. A superseded or canceled result is marked coordinated without posting. Recheck task state inside the per-thread queue before any reply.
- If a new thread message arrives during result review, stop that review as a successful deferral and process the pending message in the same per-thread loop before reviewing results again. Research answer submission saves its result and requests a coordinator wake without waiting for the review run to finish. Keep periodic polling as restart and missed-wake recovery.
- Updating a task cancels the old task, ignores any late result, and creates a new task with revised instructions; canceling a task ignores any late result. No live Pi modification or cancellation in this version. For a coding task with an existing Linear ticket, cancel that ticket and create a new one if the revised request still needs one; do not edit the old ticket description.

## Slack replies and failures

- Send one thread reply for each task as soon as its coordinator tool completes, in tool order. Coding acknowledgments link a transient short task title to the new ticket; research acknowledgments say “Looking into …” without quotation marks. Approved research results mention the source user, quote the short question once, and put the agent answer in a Slack Markdown block. Research answers start directly with findings, without a repeated question title. Do not reply to messages with no request directed at Bear Metal.
- Persist a task row before an external ticket-creation call. If Linear or Slack returns an error or an uncertain outcome, log it, mark the task failed, and do not automatically retry the external action. A ticket may exist without a Slack acknowledgment if Linear succeeded but its response was lost; this is accepted. Replayed messages must see the existing task row and must not create another task for the same request.

## Persistence

| Storage | Purpose |
| --- | --- |
| `slack_threads` | Unique `(workspace ID, channel ID, root thread_ts)` and first-mention message `ts`; identifies followed threads when events arrive. |
| `slack_processed_messages` | Unique `(workspace ID, channel ID, message ts)` and intake/processed state; no Slack message body. Covers retries and messages with no task. |
| Existing `tasks` | Type, Slack source/owner, request and quote, result, ticket/reply IDs, supersession/cancellation, and `coordinated_at` where applicable. |

SQLite's single database writer is acceptable for this deployment. Keep DB transactions short and use SQLite's internal finite busy timeout; a timed-out lock attempt fails visibly. PostgreSQL remains an option if database-write concurrency becomes a problem. Coordinator exclusivity comes from the single manager and keyed queue, not a DB transaction held during Pi execution.

## Implementation and verification

1. Extend the task contract and schema; add the two Slack tables and restart queries.
2. Add Slack event verification/intake, thread reads on incoming events, restart recovery for persisted work, and the single-manager keyed coordinator queue.
3. Add coordinator task tools, research dispatch through `buildWorkspace`, the research-answer tool, and deterministic Slack replies.
4. Verify mention inside an existing thread, untagged follow-up, self-message filtering, batched corrections, duplicate events, restart recovery, superseded research, and one message creating multiple independent tasks. Run the Bear Metal test suite and typecheck.

## Review decisions

1. Every new top-level DM to Bear Metal activates a followed thread. Bear Metal replies within that thread.
2. The coordinator payload is JSON. Place named per-message and aggregate text limits in the relevant source file. Preserve every message reference and explicit truncation metadata; the coordinator reads omitted content through tools before acting. Task summaries exclude large request and result bodies; a task-detail tool supplies them on demand.
