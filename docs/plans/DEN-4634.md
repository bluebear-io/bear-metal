# DEN-4634 — Report Pi session start and end to BlueBear

## Goal

BlueBear's Pi extension (`~/.pi/agent/extensions/bluebear.ts`) must see `session_start` and
`session_shutdown` for every Pi session Bear Metal runs: the coding worker and the Slack agent.

Verified against Pi 1.0.3:

- `AgentSession.bindExtensions()` emits `session_start`. The coding worker already calls it (DEN-4630);
  the Slack agent does not.
- `AgentSessionRuntime.dispose()` emits `session_shutdown` and then disposes the session.
  `AgentSession.dispose()` does not emit it, and both harnesses call `session.dispose()`.

## Changes

- `src/worker/pi-runtime.ts` (new): `createPiSessionRuntime()` builds an `AgentSessionRuntime` with
  `createAgentSessionRuntime()`, the default `agentDir` (`getAgentDir()`), an in-memory session manager, and
  a factory that builds services with `createAgentSessionServices()` (which constructs the default resource
  loader) and the session with `createAgentSessionFromServices()` from the caller's model runtime, model,
  and tools.
- `src/worker/pi.ts`: create the session through `createPiSessionRuntime()`, keep the existing
  `bindExtensions` call on `runtime.session`, and end through `disposePiSessionRuntime(runtime, ...)`
  (which awaits `runtime.dispose()`, see below).
- `src/worker/slack-agent.ts`: create the session through `createPiSessionRuntime()`, call
  `await session.bindExtensions({ onError })` (logging extension errors) before prompting, and end through
  `disposePiSessionRuntime(runtime, ...)`.

### Bounding extension handlers (review follow-up)

`session.abort()` cannot interrupt an extension handler, so a stuck `session_start` or `session_shutdown`
handler must not wedge either harness.

- `src/worker/until-stopped.ts` (new): the `untilStopped` helper, moved out of `pi.ts` so both harnesses share it.
- `src/worker/slack-agent.ts`: `bindExtensions` is raced against a stop signal that the time and token limits
  abort, matching the coding worker. A stuck `session_start` fails the run with the limit error and the session
  is still ended.
- `src/worker/pi-runtime.ts`: `disposePiSessionRuntime()` awaits `runtime.dispose()` for at most
  `SESSION_SHUTDOWN_GRACE_MS` (30 s). On timeout or rejection it reports through `onFailure` (both harnesses
  log an error), calls `runtime.session.dispose()` itself (reporting it through `onFailure` if it throws), and
  never rejects, so a dispose failure cannot mask
  the run's original error or skip the rest of the `finally` block (`await leaseAbort`, lease release,
  `finishAgentRun`).
- `pi.ts` and `slack-agent.ts` end sessions with `disposePiSessionRuntime()`.

## Verification

- `src/worker/pi-extensions.test.ts`: runs the worker through the real Pi runtime with an inline extension
  and asserts the order `session_start`, prompt, `session_shutdown` (reason `quit`), session dispose.
- `src/worker/slack-agent-deferral.test.ts`: asserts the Slack agent calls `bindExtensions` before the
  prompt and ends with `runtime.dispose()`, and that a never-settling `session_start` fails the run on the time
  limit while the runtime is still disposed.
- `src/worker/pi-runtime.test.ts`: `disposePiSessionRuntime()` waits for a normal dispose, disposes the session
  and reports after the grace period when `session_shutdown` hangs, and reports (instead of throwing) a dispose
  rejection, including one that arrives after the grace period, and a throwing forced `session.dispose()`.
- Forcing `session.dispose()` while `runtime.dispose()` waits on a `session_shutdown` handler does not make
  the late `runtime.dispose()` reject: in Pi 1.0.3 `AgentSession.dispose()` is idempotent (checked with a real
  runtime and a gated `session_shutdown` handler).
- `npm run typecheck` and `npm test`.
