# DEN-4168 — Document custom runtime images

## Goal

Close the public documentation gap left by [PR #144](https://github.com/bluebear-io/bear-metal/pull/144), which removed the runtime environment-builder hook. Operators asking [GitHub issue #130](https://github.com/bluebear-io/bear-metal/issues/130) — "how do I add a project-specific toolchain now?" — need a concrete, working recipe: build a custom OCI image on top of the official Bear Metal image, install the extra toolchains at image build time, and run it with a configuration module.

## Changes

Docs-only, in this repo:

- `README.md`
  - Add a new top-level section, **Custom runtime image**, between *Environment variables* and *Quick guides*.
    - Explain why toolchains must be baked into the image (runtime `apt-get`/`pip`/`npm install` inside the running container is unsupported: no runtime builder hook exists after #144, and Bear Metal deployments are expected to run with a read-only container filesystem so writes to `/var`, `/etc`, `/usr` fail).
    - Provide a copy-pasteable `Dockerfile` extending `ghcr.io/bluebear-io/bear-metal:latest` and installing an additional toolchain (e.g. Go + Python + `uv`) at build time. Keep the working directory, entrypoint, and `CMD` inherited from the base image — do not re-declare them.
    - Show the `docker build` and `docker run` invocations, including mounting the trusted configuration module and setting `BEAR_METAL_CONFIG_FILE`.
    - Cross-reference [Configuration module](#configuration-module) as the place that wires the toolchain into `customizeTask.buildWorkspace`.
  - Add the new section to the top-of-README table of contents.
- No source, CI, or Docker changes. The public base image is unchanged.

## Out of scope

- `docs/how-it-works.md` does not yet exist on `main`; it lives only on the open PR [#136](https://github.com/bluebear-io/bear-metal/pull/136) branch. The stale `../README.md#worker-environment-builder` link is corrected inside PR #136 itself (per the Linear developer decision on DEN-4168) so this PR does not need to touch a file that main does not have. After both PRs are open, whoever rebases/merges #136 must swap the stale anchor for `#custom-runtime-image` before merging.
- Do not restore the removed runtime environment builder or change any runtime behavior.
- GitHub issue #130 stays open until this guide and the #136 link correction both land.

## Verification

- Render the README locally / on GitHub and confirm the new **Custom runtime image** section appears in the ToC and anchors resolve.
- Sanity-check the example Dockerfile by tree-parsing it (matching `FROM ghcr.io/bluebear-io/bear-metal:latest`, `apt-get install -y --no-install-recommends`, `rm -rf /var/lib/apt/lists/*`) — no build required in CI; the guide is illustrative but must be syntactically valid Dockerfile.
- The `uv` install step uses `PIPX_HOME=/opt/pipx PIPX_BIN_DIR=/usr/local/bin pipx install uv` rather than `pipx install --global`, since the pipx shipped by Debian bookworm (the base image OS, via `node:24-slim`) predates the `--global` flag.
- The `docker run --read-only` example must include a writable mount (`--tmpfs /root/.bear-metal/cache-home`) for the agent cache-home path, since the base image runs as root (no `USER` directive in `Dockerfile`).
- Grep the whole repository for `worker-environment-builder` / `workerEnvironmentBuilder` to confirm no public doc still points at the removed anchor (only historical `docs/plans/DEN-2565.md` may retain the term; plan files are historical and out of scope).
- Confirm `npm run typecheck` and `npm test` still pass — expected trivially since only Markdown changes.
