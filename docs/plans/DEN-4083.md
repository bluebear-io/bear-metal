# DEN-4083 — Bear Metal ticket lifecycle and notifications

## Problem
When bear-metal opens or updates a PR, users often get **two** Slack DMs a few
minutes apart:

1. The first fires as soon as the worker finishes (ticket transitions from
   `validating` → `waiting_for_human`), while CI on the PR head SHA is still
   `queued` / `in_progress`.
2. CI then fails → manager sees `testsFailed` → re-dispatches → worker fixes it
   → second DM fires as "updated PR".

There is also no notification when bear-metal gives up because it hit
`MAX_ITERATIONS`; the ticket is silently handed back on Linear.

## Goals
1. **Only DM when the PR is actually ready for review.** Defer the
   `validating` → `waiting_for_human` transition (and the Slack DM) while any
   check run on the current head SHA is still `queued` / `in_progress`. If CI
   later fails, the existing re-dispatch path handles it; the user gets a single
   DM once CI settles green (or once bear-metal decides it can't fix it any
   more, which flows through the max-iterations path below).
2. **Notify on max-iteration hand-back.** When
   `enforceIterationLimit` gives up on a ticket, send a Slack DM to the ticket
   assignee (falling back to the shared channel) explaining that bear-metal
   stopped and the human owns it again.

Out of scope: periodic "still working, N iterations in" heartbeats — the ticket
raises the idea as speculative ("we would need to consider"), no concrete
requirement, so leave for a follow-up.

## Design

### 1. Wait for CI to finish before notifying
- `PullRequestStatus` (in `shared/integrations/github/types.ts`) gains
  `checksInProgress: boolean` — true when any check run on the PR head SHA has
  `status !== "completed"`.
- `GitHubIntegration.getPullRequestStatus` populates it from the same
  `checks.listForRef` call already used by `getFailedCheckRuns`. Refactor that
  helper to fetch check runs once and derive both `failedCheckRuns` and
  `checksInProgress` from the same list.
- `evaluateTicket` folds the per-PR `checksInProgress` into a decision-level
  `checksInProgress` flag on `TicketDecision`. It is only meaningful when
  `dispatch === false` and `phase === "active"`.
- `refreshTrackedTickets`'s "settled, transition to waiting_for_human" branch
  checks `decision.checksInProgress`. When true, skip
  `tryTransitionToWaitingForHuman` and skip the Slack send this tick — the
  ticket stays in `validating` with `notify=1` intact so the next poll will
  reconsider it.

### 2. Max-iteration Slack notification
- `SlackIntegration` gets a new `notifyMaxIterationsReached({ ticketId,
  ticketUrl, title, maxIterations, recipientEmail? })` method that formats a
  clear DM ("🐻 Reached max iterations (N) on <ticket> — needs your review").
  Follows the same DM-first-with-channel-fallback pattern as
  `notifyNeedsInput`.
- `enforceIterationLimit` gains an optional `slack?: SlackIntegration` +
  `linear` (already has it) parameter. When the limit is reached it looks up
  the assignee email and calls `notifyMaxIterationsReached`. Errors are logged
  and swallowed (same pattern as existing Slack sends). A DB event of type
  `user_notified` is recorded for the dashboard.
- `Scheduler.tick` passes `this.deps.slack` into `enforceIterationLimit`.

### 3. Bounded CI-deferral watchdog
- `Scheduler` keeps a per-ticket `Map<ticketId, number>` `ciDeferralStartedAt`
  tracking the wall-clock time of the first tick that deferred the transition
  because CI was still in progress.
- `refreshTrackedTickets` receives the map + a `ciDeferralMaxMs` bound
  (default 30 min, overridable via `SchedulerDeps.ciDeferralMaxMs`). Every
  deferred tick emits a `logger.warn` with the current deferral age, and once
  the age exceeds `ciDeferralMaxMs` the scheduler proceeds with the
  `waiting_for_human` transition anyway (logged as a warning) so a hung /
  abandoned check run cannot silently swallow the Slack DM.
- The map entry is cleared when CI settles, when the transition proceeds
  (timeout or clean settle), and when the ticket is removed from tracking.

  `PullRequestStatus`.

  `PullRequestContext`; `getPullRequestContext` fetches the paginated check-run
  list exactly once and derives both `failedCheckRuns` and `checksInProgress`

  `computeChecksInProgress(runs)` helper for unit tests.
- `src/shared/integrations/github/client.test.ts` — cover new field
  (in-progress vs completed check runs).
- `src/manager/scheduler.ts` — `TicketDecision.checksInProgress`;
  `evaluateTicket` sets it; `refreshTrackedTickets` defers transition when
  true; `enforceIterationLimit` sends the new Slack notification.
- `src/manager/scheduler.test.ts` — new cases:
  - PR settled with a check run still `in_progress` → no
    `tryTransitionToWaitingForHuman`, no dispatch, still tracked, ticket_status
    unchanged.
  - Same ticket next tick with checks now green → transition + Slack DM fires
    exactly once.
  - Max-iteration hand-back with `slack` → `notifyMaxIterationsReached` called.
- `src/shared/integrations/slack/client.ts` — add
  `notifyMaxIterationsReached` + `formatMaxIterationsReachedText`.
