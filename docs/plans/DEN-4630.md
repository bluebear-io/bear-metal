# DEN-4630 — Fire Pi extension session_start in worker sessions

## Problem

`runPiWorker` (`src/worker/pi.ts`) creates its Pi session via the SDK
`createAgentSession` but never calls `session.bindExtensions(...)`. In the Pi
SDK, `session_start` is emitted to extensions only from `bindExtensions` (the
CLI calls it itself). The BlueBear Pi extension installed by the handler under
`~/.pi/agent/extensions/` therefore never sees SessionStart for Bear Metal
dispatches.

## Changes

- `src/worker/pi.ts`: right after `createAgentSession`, `await
  session.bindExtensions({ onError })`. `onError` logs the extension error
  (`extensionPath`, `event`, `error`, `stack`) plus `ticketId` at error level
  through the worker logger. With no extensions loaded this only emits to an
  empty runner, so dispatch behavior is unchanged.
- `src/worker/pi.test.ts`: the mocked session gains a no-op `bindExtensions`.
- `src/worker/pi-extensions.test.ts` (new): runs `runPiWorker` against the real
  SDK session with a `DefaultResourceLoader` holding inline
  `extensionFactories` (isolated temp `agentDir`, stubbed `prompt`), asserting:
  - `session_start` (reason `startup`) fires before the prompt is sent;
  - an error thrown by an extension's `session_start` handler is logged as
    `pi extension error` with the event, message and ticket id.

## Verification

- New test fails before the change (no `session_start`, no log) and passes after.
- `npm test` (all existing tests) and `npm run typecheck` pass.
